# Unitree G1

  src="https://huggingface.co/datasets/huggingface/documentation-images/resolve/main/lerobot/unitree_thumbnail.jpg"

The Unitree G1 humanoid is now supported in LeRobot! You can teleoperate, train locomanipulation policies, test in sim, and more. Both 29 and 23 DoF bodies are supported, with Dex1 grippers, Dex3 hands or AmazingHands and an optional pan/tilt head camera (see [Part 5: Embodiments](#part-5-embodiments)).

## Part 1: Getting Started

### Install the Unitree SDK

Follow the [unitree_sdk2_python installation guide](https://github.com/unitreerobotics/unitree_sdk2_python#installation). Tested with `unitree_sdk2py==1.0.1` and `cyclonedds==0.10.2`:

```bash
conda create -y -n lerobot python=3.12
conda activate lerobot
git clone https://github.com/unitreerobotics/unitree_sdk2_python.git
cd unitree_sdk2_python
pip install -e .
cd ..
```

### Install LeRobot

```bash
conda install ffmpeg -c conda-forge
conda install -c conda-forge "pinocchio>=3.0.0,<4.0.0"
git clone https://github.com/huggingface/lerobot.git
cd lerobot
pip install -e '.[unitree_g1]'
```

<Tip>
  For now, pinocchio must be installed from conda-forge (not pip) to include the
  CasADi bindings needed for arm IK.
</Tip>

### Test the Installation (Simulation)

The simulation environment has its own dependencies. Check the Simulation environment dependencies: [Unitree G1 Mujoco EnvHub](https://huggingface.co/k-valentin/unitree-g1-mujoco/tree/main).

```bash
pip install mujoco loguru msgpack msgpack-numpy
```

```bash
lerobot-teleoperate \
  --robot.type=unitree_g1 \
  --robot.is_simulation=true \
  --teleop.type=unitree_g1 \
  --teleop.id=wbc_unitree \
  --robot.cameras='{"global_view": {"type": "zmq", "server_address": "localhost", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30, "warmup_s": 5}}' \
  --display_data=true \
  --robot.controller=GrootLocomotionController
```

This will launch a [MuJoCo sim instance](https://huggingface.co/k-valentin/unitree-g1-mujoco/tree/main) for the G1. You can connect a gamepad to your machine before launching in order to control the robot's locomotion in sim. We support both [HolosomaLocomotionController](https://github.com/amazon-far/holosoma) and [GrootLocomotionController](https://github.com/NVlabs/GR00T-WholeBodyControl) via `--robot.controller`.

- Press `9` to release the robot
- Press `7` / `8` to increase / decrease waist height

### Connect to the Physical Robot

The G1's Ethernet IP is fixed at `192.168.123.164`. Your machine must have a static IP on the same subnet: `192.168.123.x` where `x ≠ 164`.

```bash
# Replace 'enp131s0' with your ethernet interface name (check with `ip a`)
sudo ip addr flush dev enp131s0
sudo ip addr add 192.168.123.200/24 dev enp131s0
sudo ip link set enp131s0 up
```

### SSH into the Robot

```bash
ssh unitree@192.168.123.164
# Password: 123
```

### Share Internet via Ethernet

The G1 needs internet access to clone repos and install packages. Share your laptop's connection over Ethernet:

**On your laptop:**

```bash
sudo sysctl -w net.ipv4.ip_forward=1

# Replace wlp132s0f0 with your WiFi interface name
sudo iptables -t nat -A POSTROUTING -o wlp132s0f0 -s 192.168.123.0/24 -j MASQUERADE
sudo iptables -A FORWARD -i wlp132s0f0 -o enp131s0 -m state --state RELATED,ESTABLISHED -j ACCEPT
sudo iptables -A FORWARD -i enp131s0 -o wlp132s0f0 -j ACCEPT
```

**On the G1:**

```bash
sudo ip route del default 2>/dev/null || true
sudo ip route add default via 192.168.123.200 dev eth0
echo "nameserver 8.8.8.8" | sudo tee /etc/resolv.conf

# Verify
ping -c 3 8.8.8.8
```

### (Optional) Enable WiFi on the Robot

For wireless SSH access, you can enable WiFi on the G1 (it's blocked by default):

```bash
sudo rfkill unblock all
sudo ip link set wlan0 up
sudo nmcli radio wifi on
sudo nmcli device set wlan0 managed yes
sudo systemctl restart NetworkManager
```

**Connect to a WiFi network:**

```bash
nmcli device wifi list

sudo nmcli connection add type wifi ifname wlan0 con-name "YourNetwork" ssid "YourNetwork"
sudo nmcli connection modify "YourNetwork" wifi-sec.key-mgmt wpa-psk
sudo nmcli connection modify "YourNetwork" wifi-sec.psk "YourPassword"
sudo nmcli connection modify "YourNetwork" connection.autoconnect yes
sudo nmcli connection up "YourNetwork"

ip a show wlan0
```

You can then SSH over WiFi instead of Ethernet:

```bash
ssh unitree@<ROBOT_WIFI_IP>
# Password: 123
```

## Part 2: Teleoperation & Locomotion

### Run the Robot Server

On the robot (from `~/lerobot`):

```bash
cd ~/lerobot
python src/lerobot/robots/unitree_g1/run_g1_server.py --camera
```

### Run the Locomotion Policy

You can run the teleoperation client from your laptop over Ethernet, over WiFi (experimental), or directly on the robot itself. Mind potential latency introduced by your network.

**From your laptop:**

```bash
lerobot-teleoperate \
  --robot.type=unitree_g1 \
  --robot.is_simulation=false \
  --robot.robot_ip=<ROBOT_IP> \
  --teleop.type=unitree_g1 \
  --teleop.id=wbc_unitree \
  --robot.cameras='{"global_view": {"type": "zmq", "server_address": "<ROBOT_IP>", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30}}' \
  --display_data=true \
  --robot.controller=HolosomaLocomotionController
```

We support both [GrootLocomotionController](https://github.com/NVlabs/GR00T-WholeBodyControl) and [HolosomaLocomotionController](https://github.com/amazon-far/holosoma) via `--robot.controller`.

### Dataset layout with a locomotion controller

With `--robot.controller`, the controller owns the legs and waist, so they are not recorded, and
locomotion is recorded as absolute commands instead of raw remote sticks. This follows NVIDIA's
GR00T N1.7 G1 convention (`navigate_command`, `base_height_command`, no lower body in the state).

| Feature             | Columns                                                                                   |
| ------------------- | ----------------------------------------------------------------------------------------- |
| `observation.state` | the 14 arm joints (`kLeftShoulderPitch.q` … `kRightWristYaw.q`)                           |
| `action`            | the same 14 arm targets, `kNavVx.cmd`, `kNavVy.cmd`, `kNavYawRate.cmd`, `kBaseHeight.cmd` |

That is 14 / 18 columns with GR00T and 14 / 17 with Holosoma, which has no height command. Without
a controller, all 29 joints are recorded in both, as before.

- **Navigation command:** `kNavVx.cmd` / `kNavVy.cmd` (forward / left) and `kNavYawRate.cmd`
  (counter-clockwise) are derived from the remote sticks as `(ly, −lx, −rx)` with the same ±1 range
  the controllers used before. Both controllers use them directly, so a policy trained on them can
  command walking. Holosoma still applies its 0.1 dead-zone and ±0.3 clip.
- **Base height:** GR00T keeps a base-height command (default 0.74 m, range 0.50–1.00 m) that R1 /
  R2 raise / lower at 0.05 m/s. `kBaseHeight.cmd` records it as an absolute value in m, matching
  NVIDIA's `base_height_command`, and the controller uses it directly. Disable it with
  `--robot.base_height_action=false`.
- `get_observation()` still returns every joint, the IMU and the raw remote; only the recorded
  features change.

These datasets are not column-compatible with earlier G1 controller-mode datasets, which recorded
29 state columns and `remote.lx/ly/rx/ry`.

## Part 3: Loco-Manipulation with the Homunculus Exoskeleton

We provide a loco-manipulation solution via the Homunculus Exoskeleton — an open-source 7 DoF exoskeleton for whole-body control. Check it out [here](https://github.com/nepyope/hmc_exo).

### Calibrate

```bash
lerobot-calibrate \
  --teleop.type=unitree_g1 \
  --teleop.left_arm_config.port=/dev/ttyACM1 \
  --teleop.right_arm_config.port=/dev/ttyACM0 \
  --teleop.id=exo
```

During calibration move each joint through its entire range. After fitting, move the joint in a neutral position and press `n` to advance.

### Record a Dataset

```bash
lerobot-record \
  --robot.type=unitree_g1 \
  --robot.is_simulation=true \
  --robot.cameras='{"global_view": {"type": "zmq", "server_address": "localhost", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30}}' \
  --teleop.type=unitree_g1 \
  --teleop.left_arm_config.port=/dev/ttyACM1 \
  --teleop.right_arm_config.port=/dev/ttyACM0 \
  --teleop.id=exo \
  --dataset.repo_id=your-username/dataset-name \
  --dataset.single_task="Test" \
  --dataset.num_episodes=2 \
  --dataset.episode_time_s=5 \
  --dataset.reset_time_s=5 \
  --dataset.push_to_hub=true \
  --dataset.streaming_encoding=true \
  --dataset.encoder_threads=2
```

> **Note:** Omit `--teleop.left_arm_config.port` and `--teleop.right_arm_config.port` if you're only using the joystick.

Example dataset: [nepyope/unitree_box_move_blue_full](https://huggingface.co/datasets/nepyope/unitree_box_move_blue_full)

## Part 4: Training & Inference

### Train

```bash
python src/lerobot/scripts/lerobot_train.py \
  --dataset.repo_id=your-username/dataset-name  \
  --policy.type=pi05 \
  --output_dir=./outputs/pi05_training \
  --job_name=pi05_training \
  --policy.repo_id=your-username/your-repo-id \
  --policy.pretrained_path=lerobot/pi05_base \
  --policy.compile_model=true \
  --policy.gradient_checkpointing=true \
  --wandb.enable=true \
  --policy.dtype=bfloat16 \
  --policy.freeze_vision_encoder=false \
  --policy.train_expert_only=false \
  --steps=3000 \
  --policy.device=cuda \
  --batch_size=32
```

### Inference with RTC

Once trained, we recommend deploying policies using inference-time RTC:

```bash
lerobot-rollout \
  --strategy.type=base \
  --policy.path=your-username/your-repo-id \
  --policy.device=cuda \
  --robot.type=unitree_g1 \
  --robot.is_simulation=false \
  --robot.controller=HolosomaLocomotionController \
  --robot.cameras='{"global_view": {"type": "zmq", "server_address": "<ROBOT_IP>", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30}}' \
  --task="task_description" \
  --duration=1000 \
  --fps=30 \
  --inference.type=rtc
```

## Part 5: Embodiments

One robot type, `unitree_g1`, covers every G1 variant. Pick the body, end effector, head mount and
head sensor with four config fields, the same options as the MuJoCo sim's `BODY` / `END_EFFECTOR` /
`HEAD_MOUNT` / `HEAD_SENSOR`:

| Field                  | Values                                                                                                                                                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--robot.body`         | `29dof` (default), `23dof` (no waist roll/pitch, no wrist pitch/yaw)                                                                                                                                                       |
| `--robot.end_effector` | `rubber_hand` (default, Unitree's stock passive hand), `none` (bare wrist), `dex1` (Unitree Dex1-1 gripper), `dex3` (Unitree Dex3-1 hand), `amazing_hand` (Pollen Robotics AmazingHand, 8 Feetech SCS0009 servos per hand) |
| `--robot.head_mount`   | `fixed` (default, the stock head), `pan_tilt` (Dynamixel XL330 pan/tilt)                                                                                                                                                   |
| `--robot.head_sensor`  | `d435i` (default, the stock Intel RealSense D435i), `d455` (Intel RealSense D455)                                                                                                                                          |

Any combination works: every end effector mounts on either body, and any sensor on either head
mount. `rubber_hand` and `none` have no joints, so they add nothing to the recorded features. The
dataset `robot_type` and the calibration id are `unitree_g1-<body>-<end_effector>-<head_mount>-<head_sensor>`,
every field always present (the 23dof body with its `--robot.revision`), so `robot_type.split("-")`
recovers them, e.g. `unitree_g1-29dof-rubber_hand-fixed-d435i` (a stock G1),
`unitree_g1-23dof_rev_1_0-dex3-fixed-d435i` or `unitree_g1-23dof_rev_1_0-amazing_hand-pan_tilt-d455`.

| Embodiment                 | How the extras are driven                                                                    |
| -------------------------- | -------------------------------------------------------------------------------------------- |
| `dex3`                     | DDS `rt/dex3/{left,right}/{cmd,state}` (`HandCmd_` / `HandState_`), 7 joints per hand        |
| `dex1`                     | DDS `rt/dex1/{left,right}/{cmd,state}` (`MotorCmds_` / `MotorStates_`), 1 position per side  |
| `amazing_hand`, `pan_tilt` | head/hand ZMQ bridge (ports 6002/6003) to the Feetech hand bus and/or the Dynamixel head bus |

### Joint layout

Every embodiment records the stock layout with its extras appended: the 29-slot SDK body (or the
14 arm joints with a locomotion controller), then the head, then the hands, then (with a
controller) the navigation and base-height commands. All keys follow the Unitree SDK style
(`k` + CamelCase); `.q` is a position (rad, or m for `dex1`), `.closure` a hand closure in [0, 1].

| Part            | Keys                                                                                                                                                                   |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Body            | `kLeftHipPitch.q` … `kRightWristYaw.q`, SDK slots 0–28 (`G1_29_JointIndex`)                                                                                            |
| Head            | `kHeadYaw.q` (pan, Dynamixel ID 1), `kHeadPitch.q` (tilt, ID 2)                                                                                                        |
| `dex3` hands    | `k{Left,Right}Hand{Thumb0,Thumb1,Thumb2,Middle0,Middle1,Index0,Index1}.q`                                                                                              |
| `dex1` grippers | `k{Left,Right}Gripper.q` (finger travel in m, 0.0245 open)                                                                                                             |
| `amazing_hand`  | `kLeftHandMotor11.q` … `kLeftHandMotor18.q`, `kRightHandMotor1.q` … `kRightHandMotor8.q` (by Feetech motor ID; per hand, 2 servos each for index, middle, ring, thumb) |

**Unused SDK slots.** The `23dof` body is a 29-slot SDK message with no motor at slots 13, 14
(waist roll/pitch) and 20, 21, 27, 28 (wrist pitch/yaw). Their gains are zeroed and they are never
commanded; `get_observation` reports them as exactly 0.0, so the columns stay compatible with
`29dof` datasets.

**`revision` / `mode_machine`.** With the `23dof` body, `--robot.revision` (`base` or `rev_1_0`,
default) must match the robot's DDS `mode_machine` (1 or 4). `connect()` raises `ValueError` on a
mismatch before sending any command; `--robot.check_mode_machine=false` skips the check.

### Hand representation

`--robot.hand_representation` chooses how any hand appears in `action` and `observation.state`:

| Value               | Hand keys                                                          |
| ------------------- | ------------------------------------------------------------------ |
| `closure` (default) | `kLeftHand.closure`, `kRightHand.closure`                          |
| `per_motor`         | every hand joint or servo (16 `amazing_hand`, 14 `dex3`, 2 `dex1`) |

A closure `c` is mapped to the hand's joints by interpolating linearly between its open and closed
poses (`end_effectors.py`: `AMAZING_HAND`, `DEX3`, `DEX1`); values outside [0, 1] are clipped. The
measured closure is the mean, over the joints, of each joint's position along its open→closed range.
In `closure` mode `get_observation()` also returns the per-joint values, but they aren't recorded.

For the 23dof AmazingHand robot, `observation.state` / `action` have 33 / 33 columns without a
controller and 18 / 22 with `GrootLocomotionController` (47 / 47 and 32 / 36 with `per_motor`).

### Robot server

The server gains flags for the extras:

```bash
# Dex3 hands (or --hands dex1)
python src/lerobot/robots/unitree_g1/run_g1_server.py --camera --hands dex3

# 23dof + AmazingHand + pan/tilt D455
python src/lerobot/robots/unitree_g1/run_g1_server.py \
  --headhand --camera --camera-type intelrealsense --camera-serial <D455_SERIAL>
```

- `--hands dex3|dex1` bridges the hand DDS topics on ZMQ ports 6010–6017.
- `--headhand` runs the head/hand bridge (`HeadHandServer`, ports 6002/6003) on the Dynamixel head
  bus (`--head-port`, default `/dev/ttyCH341USB0`) and the Feetech hand bus (`--hand-port`,
  default `/dev/ttyACM0`). `--no-head` / `--no-hands` leave one bus out, for a head without
  AmazingHands or AmazingHands without the head. `--no-handshake` skips the bus handshake for
  firmware that doesn't answer it; `--headhand-rate` sets the state rate (default 50 Hz).
- On startup the server prints `mode_machine=<n>`; check it against `--robot.revision`.

### AmazingHand + pan/tilt D455 setup (Jetson)

1. Install LeRobot with the `unitree_g1` extra (it includes the Dynamixel, Feetech, gamepad and
   RealSense dependencies).
2. Add your user to `dialout` for the head/hand serial ports: `sudo usermod -aG dialout $USER`, then
   log in again. Pin drifting device names with a udev rule on `ID_SERIAL_SHORT`.
3. The `pyrealsense2` wheel is x86_64 only; on the Jetson build librealsense from source
   ([guide](https://github.com/IntelRealSense/librealsense/blob/master/doc/installation_jetson.md)).
4. Scan the buses: `python -m lerobot.robots.unitree_g1.headhand_devices scan` should report model
   `1200` (XL330-M288) for head IDs 1–2 and `1284` (SCS0009) for hand IDs 1–8 and 11–18. `None`
   means no reply: check wiring and IDs.
5. Find the D455 serial with `RealSenseCamera.find_cameras()`
   (`lerobot.cameras.realsense.camera_realsense`).

<Tip warning={true}>
  The server releases Unitree's built-in balance controller: there is no fall
  catching. Use a gantry unless you are testing a locomotion controller in a
  cleared area. Without a controller the legs hold their connect-time pose;
  `--robot.freeze_legs=true` makes them limp instead. `disconnect()`
  zero-torques the body, but the AmazingHand servos keep torque: run `python -m
  lerobot.robots.unitree_g1.headhand_devices torque-off` on the Jetson (or
  power-cycle).
</Tip>

### Force limiting

The AmazingHand servos (SCS0009) have no RAM torque-limit register, so the head/hand bridge limits
force in software, per servo, so that closing on an object or a stall does not break the printed
parts or the servos. Each hand goal is kept within `--hand-max-err-ticks` of the present position
(bounding the P-controller force in both directions). A servo whose `Present_Load` stays above
`--hand-load-limit` (per mille) for `--hand-overload-s` seconds backs off by `--hand-backoff-ticks`
away from where it was pushing and holds there until the operator opens the hand. A servo at or above
`--hand-temp-limit` degrees C is torqued off until it is 5 degrees cooler.

It is on by default with `--headhand` (`--no-hand-force-limit` disables it). Defaults are
`--hand-max-err-ticks 30`, `--hand-load-limit 500`, `--hand-overload-s 0.3`,
`--hand-backoff-ticks 15` and `--hand-temp-limit 65`; they are starting points to tune on the
hardware (`python -m lerobot.robots.unitree_g1.headhand_devices loads [--loop]` prints each servo's
position, load and temperature). It adds a `Present_Load` read per servo to every cycle: if the
server logs that a cycle took longer than `1/--headhand-rate`, lower the rate. Nothing is written to
the servos' EEPROM.

### Calibrate the head and hands

Only the head/hand bridge motors need calibration (the body and Dex hands report joint angles):

```bash
lerobot-calibrate \
  --robot.type=unitree_g1 --robot.body=23dof --robot.end_effector=amazing_hand --robot.head_mount=pan_tilt --robot.head_sensor=d455 \
  --robot.is_simulation=false --robot.robot_ip=192.168.123.164 --robot.id=lab_g1
```

1. Center the head (camera forward, level) and press Enter.
2. Turn the head to the robot's left and tilt it up slightly, then press Enter: this sets each
   servo's direction.
3. Sweep pan and tilt to both mechanical stops, then press Enter.
4. Hands: press Enter to import the lab's per-servo zero trims, or type `i` for an interactive
   neutral-pose + sweep calibration.

The calibration is written to
`~/.cache/huggingface/lerobot/calibration/robots/<robot_type>/<id>.json`. Calibration files that use
the pre-rename motor names (`xl330_joint`, `d455_joint`, `{side}_hand_finger{i}_motor{j}`) are
renamed on load. A calibration made with the former `unitree_g1_23dof_ah8_d455_2dof` robot type
can be moved to `.../robots/unitree_g1-23dof_rev_1_0-amazing_hand-pan_tilt-d455/`.

### Teleoperate with a gamepad or the keyboard

`unitree_g1_gamepad` (DualShock 4 / Xbox via pygame) and `unitree_g1_keyboard` (no pad) work with
every embodiment: they emit the body, head, every end effector's joints and the closures, and the
robot keeps the keys it has. They start from the robot's measured pose, so nothing moves at connect;
`--teleop.initial_positions='{"kLeftElbow.q": 1.2}'` pins chosen keys instead.

```bash
lerobot-record \
  --robot.type=unitree_g1 --robot.body=23dof --robot.end_effector=amazing_hand --robot.head_mount=pan_tilt --robot.head_sensor=d455 \
  --robot.is_simulation=false --robot.robot_ip=192.168.123.164 --robot.id=lab_g1 \
  --robot.controller=GrootLocomotionController \
  --robot.cameras='{"head_camera": {"type": "zmq", "server_address": "192.168.123.164", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30}}' \
  --teleop.type=unitree_g1_gamepad \
  --dataset.repo_id=your-username/dataset-name \
  --dataset.single_task="Test" \
  --dataset.num_episodes=2 \
  --dataset.episode_time_s=5 \
  --dataset.reset_time_s=5
```

| Gamepad (DualShock 4 / Xbox) | Keyboard        | Action                                                              |
| ---------------------------- | --------------- | ------------------------------------------------------------------- |
| D-pad left/right, up/down    | Arrow keys      | Head pan / tilt (0.8 rad/s; `--teleop.invert_tilt=true` flips tilt) |
| R1 / L1 (RB / LB)            | `e` / `q`       | Hold to close the right / left hand (closure 0 → 1 at 2.0/s)        |
| L2 / R2 (LT / RT)            | `t` / `g`       | Raise / lower `kBaseHeight.cmd` (`GrootLocomotionController`)       |
| Left stick                   | `w a s d`       | Walk: `kNavVx.cmd` / `kNavVy.cmd`, with a controller                |
| Right stick x                | `j` / `l`       | Turn: `kNavYawRate.cmd`                                             |
| Triangle / Cross / Square    | `y` / `n` / `r` | End episode: success / failure / rerecord                           |
| Options (Start)              | Space           | Hold for intervention                                               |

The gamepad has presets for SDL2's HIDAPI PS4 driver (`dualshock4_hidapi`, default), the kernel
`hid-sony` driver (`dualshock4_kernel`) and Xbox pads (`xbox`): `--teleop.preset=...`, or override
single indices (`--teleop.layout.button_rb=<idx>`). Find your pad's indices with
`python -m lerobot.teleoperators.unitree_g1_gamepad.gamepad_input --seconds 30`. The keyboard reads
keys from a small window by default (works on Wayland); `--teleop.backend=pynput` captures them
globally on X11.

### Teleoperate with an XR headset (Quest 3)

`unitree_g1_xr` drives the arms from the controllers' (or tracked hands') wrist poses, the pan/tilt head
from the headset and the hands from the triggers. It is a thin adapter over our
[xr_teleoperate fork](https://github.com/MrKeith99/xr_teleoperate)'s `xr_teleoperate.core`, whose arm IK
is built from the sim's composed model of the same embodiment, so it covers every body and end effector.
Give it the robot's four embodiment fields; it refuses a robot of another embodiment.

```bash
pip install -e ".[unitree_g1_xr]"
# televuer pins numpy<2, so install it without its dependencies from the fork's checkout
git clone --recurse-submodules https://github.com/MrKeith99/xr_teleoperate
pip install -e xr_teleoperate/teleop/televuer --no-deps
# The headset needs HTTPS: a self-signed certificate where televuer looks for it
mkdir -p ~/.config/xr_teleoperate && cd ~/.config/xr_teleoperate && \
  openssl req -x509 -nodes -days 365 -newkey rsa:2048 -keyout key.pem -out cert.pem -subj "/CN=xr"

lerobot-teleoperate \
  --robot.type=unitree_g1 --robot.body=23dof --robot.end_effector=amazing_hand --robot.head_mount=pan_tilt --robot.head_sensor=d455 \
  --robot.is_simulation=true --robot.controller=GrootLocomotionController \
  --teleop.type=unitree_g1_xr --teleop.body=23dof --teleop.end_effector=amazing_hand --teleop.head_mount=pan_tilt --teleop.head_sensor=d455
```

Open `https://<host>:8012` in the Quest browser (accept the certificate), enter VR, then stand facing
the robot's forward direction and press A.

| Quest controllers            | Action                                                                                                                                                |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| A                            | Engage / disengage: recenter on your facing direction, start from the arm pose; disengaged holds every target, no walking                             |
| Controller poses             | Arm IK targets (`--teleop.max_arm_speed_rad_s`, default 3.0)                                                                                          |
| Headset yaw / pitch          | `kHeadYaw.q` / `kHeadPitch.q` with a pan/tilt head (`--teleop.invert_head_pitch`)                                                                     |
| Triggers                     | Left / right hand closure                                                                                                                             |
| Left stick, right x          | Walk / turn: `kNavVx/Vy/YawRate.cmd`                                                                                                                  |
| X / Y                        | Hold to lower / raise `kBaseHeight.cmd`                                                                                                               |
| Right stick click            | End the episode (success); during the reset phase, skip the rest of it                                                                                |
| Left stick click             | Discard and re-record the episode                                                                                                                     |
| Both grips, 1 s (disengaged) | Start / stop locomotion on the real robot; in sim, attach / release the elastic band (`--robot.sim_band_toggle_button=null` disables the sim gesture) |

With `lerobot-record`, each episode starts only once the operator is ready: locomotion runs (real robot with
a controller) or the sim elastic band is released, and the XR teleoperator is engaged with A. Pass
`--wait_for_operator=false` to start episodes immediately as before.

#### Locomotion start on the real robot

With a locomotion controller on the real robot, the walking policy does not start at connect. The legs and
waist ramp over 3 s (`--robot.stand_ramp_s`) from their measured pose to the controller's standing pose and
hold it with the controller's gains (keep the robot on the gantry). Lower it until the feet carry weight,
then hold both grips for 1 s while disengaged to start GR00T; do it again to stop (the legs then hold their
current pose). A start requested during the ramp is refused. `--robot.locomotion_start_gate=false` restores
starting the controller at connect. Episodes start only once locomotion runs and the teleop is engaged.

In sim, at the end of each episode the XR teleoperator disengages and resets the sim: the robot is back
on the band at its start pose. Release the band with both grips, then press A, and the next episode
starts. With this and the operator gate, `--dataset.reset_time_s=0` is recommended for XR sim recording.
`--teleop.reset_sim_on_episode_end=false` disables the automatic reset.

Nothing moves until A; the arms then move to your pose at `--teleop.engage_arm_speed_rad_s` (0.5) before following at full speed, and targets hold while tracking is lost. `--teleop.input_mode=hand` uses hand
tracking (pinch closes the hand; it engages when tracking starts).

By default the headset shows pass-through (the room). `--teleop.display_mode=ego` shows the robot's head
camera in a small window with the room around it, `immersive` fills the view; the Quest's "Pass-through"
button switches back to the room. The frame is `--teleop.display_camera` (default `head_camera`) from the
robot's cameras, resized to `--teleop.display_image_shape` (480 640) at up to `--teleop.display_fps` (30).
If the camera is missing a warning lists the image keys present. A sim example with the head camera:

```bash
lerobot-teleoperate \
  --robot.type=unitree_g1 --robot.body=23dof --robot.end_effector=amazing_hand --robot.head_mount=pan_tilt --robot.head_sensor=d455 \
  --robot.is_simulation=true --robot.controller=GrootLocomotionController \
  --robot.cameras='{"head_camera": {"type":"zmq","server_address":"127.0.0.1","port":5555,"camera_name":"head_camera","width":640,"height":480,"fps":30,"warmup_s":5}}' \
  --teleop.type=unitree_g1_xr --teleop.body=23dof --teleop.end_effector=amazing_hand --teleop.head_mount=pan_tilt --teleop.head_sensor=d455 \
  --teleop.display_mode=ego
```

### Simulation

[`k-valentin/unitree-g1-mujoco`](https://huggingface.co/k-valentin/unitree-g1-mujoco), the default
`--robot.sim_env_repo_id`, composes every combination at load time; the robot passes its embodiment
to it as `UNITREE_G1_MUJOCO_BODY` / `_END_EFFECTOR` / `_HEAD_MOUNT` / `_HEAD_SENSOR`. On the 23dof body a hand sits where it
would on a 29dof arm with its wrist pitch/yaw at zero; the Dex and AmazingHand mounts on the other
body are placeholders until there is adapter CAD. With the head or the AmazingHand the sim runs the
same head/hand ZMQ bridge on localhost as the Jetson, and writes a default head/hand calibration.

```bash
# 23dof + AmazingHand + pan/tilt D455 with the gamepad. PS toggles the elastic band; the sim reset
# moves to Share (8) because Options (9) is the gamepad's intervention button.
lerobot-teleoperate \
  --robot.type=unitree_g1 --robot.body=23dof --robot.end_effector=amazing_hand --robot.head_mount=pan_tilt --robot.head_sensor=d455 \
  --robot.is_simulation=true --robot.id=sim --robot.sim_reset_button=8 \
  --teleop.type=unitree_g1_gamepad \
  --robot.cameras='{"head": {"type":"zmq","server_address":"127.0.0.1","port":5555,"camera_name":"head_camera","width":640,"height":480,"fps":30,"warmup_s":5}}' \
  --display_data=true

# 23dof + Dex3 hands with the keyboard
lerobot-teleoperate \
  --robot.type=unitree_g1 --robot.body=23dof --robot.end_effector=dex3 --robot.is_simulation=true \
  --teleop.type=unitree_g1_keyboard
```

Other sim options still come from `UNITREE_G1_MUJOCO_<OPTION>` environment variables (`ONSCREEN=0`
for headless, `JOYSTICK_TYPE=dualshock4|xbox|switch`, `HEADHAND_STATE_PORT`, `HEADHAND_CMD_PORT`).
While the elastic band holds the robot the locomotion controller is paused and the legs go limp. On
GNOME Wayland launch with `PYGLFW_LIBRARY_VARIANT=x11 SDL_VIDEODRIVER=x11` (GLFW and SDL2 otherwise
deadlock in libdecor-gtk). After `disconnect()` the process may not exit on its own because of
CycloneDDS finalizers; kill it and its `multiprocessing.spawn` image-publisher child.

<Tip>
  With Python 3.12, `unitree_sdk2py` needs CycloneDDS 0.10.x built from source: build the
  `releases/0.10.x` branch, `export CYCLONEDDS_HOME=<install prefix>` in every shell, then
  `pip install --no-binary cyclonedds "cyclonedds==0.10.2"` and `pip install --no-deps -e <unitree_sdk2_python>`.
</Tip>

### Troubleshooting

- **`mode_machine=<n> does not match revision ...`**: pass the `--robot.revision` matching the
  server's `mode_machine=<n>` line (`base` = 1, `rev_1_0` = 4), or `--robot.check_mode_machine=false`.
- **Head/hand connect times out**: the robot waits `--robot.headhand_timeout_s` (5 s) for the first
  head/hand state. Check that the server printed `Head/hand bridge started`, that
  `--robot.headhand_state_port` / `--robot.headhand_cmd_port` match its ports, and that no firewall
  blocks 6002/6003.
- **"Head/hand state is stale"**: the last state is older than `--robot.headhand_stale_warn_s`
  (0.5 s); the bridge thread died or the network stalled. Check the server log.
- **Handshake errors on the head or hand bus**: retry the server with `--no-handshake`.
- **Dex1 on real hardware**: the gripper's motor range (`DEX1_REAL_OPEN_Q` / `DEX1_REAL_CLOSED_Q`
  in `dex_hands.py`) is not yet verified on hardware.
